# 15: Compliance and security for ChordusAM

**Author:** SEC, Compliance and Security lead (discovery team) | **Date:** 9 November 2026 | **Upstream read:** `docs/discovery/00-brief.md`, `docs/PLAN.md` (sections 2, 4, 5, 9, 12, 13, 15, 16), `docs/phase-0.md`, `supabase/migrations/20261105000000_phase0_foundation.sql`, `supabase/rollbacks/20261105000000_phase0_foundation.down.sql`, `lib/auth/*.ts`, `lib/audit.ts`, `lib/env.ts`, `middleware.ts`, `app/login/*`, `app/auth/callback/route.ts`, `scripts/seed-demo-users.ts`, `supabase/config.toml`, `.github/workflows/ci.yml`, `docs/discovery/research/R2-hris-payroll-sri-lanka.md`, `R3-pos-booking-finance.md`, `R4-creative-ops-rights.md`.

**Summary.** ChordusAM will hold the most sensitive data AMPL has: NIC numbers, bank details, salaries, medical leave notes, attendance records, freelancer tax details, client money, and consent records for talent faces and voices (including AI likeness). The core of Sri Lanka's Personal Data Protection Act No. 9 of 2022 (as amended by Act No. 22 of 2025) takes effect on **1 January 2027**, seven weeks from today. From that date AMPL must show a lawful basis for each kind of data, keep it no longer than needed, secure it, appoint a Data Protection Officer (DPO) and handle breaches. Data subject rights (Part II) and the penalty regime (Part VII) wait for a later order, but building for them now is cheap. Payments can stay out of PCI DSS scope if ChordusAM never sees card numbers: PayHere's hosted checkout for online payments, standalone bank terminals and static LankaQR in the studio. Phase 0 is a good base: roles come from the database, RLS is on, there is an append-only audit log and every page and API route checks access on the server. Before the first real personal data goes in (Phase 1, employees with NIC), eight gaps need fixing. The most serious are that the audit trigger copies whole rows (it would copy salaries and NICs in plain text into the audit log), there is no MFA, the demo seed script can create a known-password Admin in a real project, no Vercel region is set (so personal data would be processed in the US by default), and the single-role model cannot express segregation of duties or a second legal entity. This document sets out the regulatory register, data classification, security architecture, a STRIDE threat model for six high-risk flows, a controls catalogue (candidate IDs `NFR-SEC-*`, `NFR-PRIV-*`, `NFR-AUD-*`) with a segregation of duties matrix, the Phase 0 review, and a compliance roadmap.

> **Method and limits.** Web searches were run on 9 November 2026. This session's network blocked direct fetches of `dpa.gov.lk`, `documents.gov.lk`, `ft.lk` and `supabase.com`, so most facts come from search-result summaries of the cited pages, not a full read. Where sources conflict or only secondary sources exist, I write "(unverified)". **Nothing here is legal advice.** Items marked "legal review" need AMPL's Sri Lankan lawyer or accountant before they become rules in `lib/rules/` or contract templates.

> **IDs.** The BRD (`docs/discovery/10-brd.md`) does not exist yet. Business requirements are cited by research ID (for example `R2-33`, `R4-F06`) and module code (for example "BR-VP"). The `NFR-SEC-NNN`, `NFR-PRIV-NNN` and `NFR-AUD-NNN` IDs in section 6 are **candidates for the BA to adopt** in `10-brd.md`, following brief section 7. Controls are referred to by these IDs throughout.

### 4.2 Authorisation: RBAC, entity scoping and RLS

**Model.** Keep the Phase 0 principle (role from the database, checked three times: middleware convenience, server guard, RLS). Extend it:

1. **Tenancy and entities.** Add `entities` (AMPL Colombo, Media Digital SG later). Every business row carries `entity_id`. If the SaaS option is pursued, add `tenant_id` above `entity_id` now, defaulting to one tenant; retrofitting it later touches every policy.
2. **Grants table, not one role column.** `user_entity_roles (user_id, entity_id, role, granted_by, approved_by, valid_from, valid_to)`. Roles stay coarse (employee, hr, finance, admin) plus **permissions** for the exceptions PLAN already has (`can_request_payments`) and new ones: `salary_viewer`, `vendor_bank_editor`, `payment_releaser`, `pos_cashier`, `pos_supervisor`, `producer`, `dpo`. `profiles.role` can stay as the "primary role" for navigation.
3. **Helpers.** `has_entity_role(p_entity uuid, variadic roles app_role[])` and `has_permission(p_entity uuid, p_perm text)`, both `security definer`, `stable`, `search_path = ''`, like the Phase 0 helpers. In policies, do not pass a row column to a helper: `(select f(entity_id, …))` still runs once per row. Use the entity-array form `entity_id = any ((select app.perm_entities('perm'))::uuid[])`, which runs once per statement (measured 50 times faster in `22a-foundation-spike.md` §3f; pattern in `20-solution-design.md` §7.3). Keep the two-argument helpers for single-row checks inside functions.
4. **Policy patterns.**
   - Own rows: `employee_id = (select public.current_employee_id())`.
   - Role in entity: `using ((select public.has_entity_role(entity_id, 'hr', 'admin')))`.
   - **Restrictive MFA policy** on every Restricted table: `as restrictive for all to authenticated using ((auth.jwt() ->> 'aal') = 'aal2' or <row is the caller's own>)`.
   - State-based: Finance sees `payroll_runs` only where `status in ('approved','sent_to_finance','paid')` (PLAN 12).
   - **No self-approval** in the database: approval inserts check `approver_id <> requester_id` in a trigger, not only in the UI.
   - Column protection: Restricted columns live in their own table or are only returned by a `security definer` RPC that checks the permission and writes a read audit (section 4.4). Postgres RLS is row-level; it cannot hide one column from a role that can read the row.
5. **Server guards.** Extend `Requirement` in `lib/auth/authorize.ts` to `{ permission, entityId?, aal? }` so pages and API routes check the same thing RLS checks.
6. **Tests.** For every new table: one RLS test per role per operation, including negatives, an `aal1` versus `aal2` test for Restricted tables, and a cross-entity test (an SG user cannot see LK rows). CLAUDE.md already requires RLS tests per table.

### 4.3 Field-level encryption and key management

**Recommendation: application-level envelope encryption, not pgsodium.** Supabase marks pgsodium "pending deprecation" and does not recommend new use of it, including Transparent Column Encryption; Vault stays but its internals move off pgsodium ([Supabase pgsodium page](https://supabase.com/docs/guides/database/extensions/pgsodium)). Keys held inside the same database as the data also protect little against a database or backup leak.

| Item            | Design                                                                                                                                                                                                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Algorithm       | AES-256-GCM with a random 96-bit nonce per value, using Node's `crypto` in a `server-only` module (`lib/crypto/fields.ts`). Ciphertext stored as `v1:<nonce>:<ciphertext>:<tag>` (base64), with the key version in front                                                                                         |
| What            | NIC, passport, TIN, EPF member number, bank account number and branch, PayHere customer tokens, medical leave reason text                                                                                                                                                                                        |
| Search          | A **blind index**: HMAC-SHA256 of the normalised value with a separate key, stored in its own column. Supports PLAN 5.1 duplicate detection ("name plus NIC or bank account") and "same bank account on two vendors or an employee and a vendor" checks without decrypting                                       |
| Keys            | Data key and index key as Vercel **production-only, server-only** environment variables (`CHORDUS_FIELD_KEY_V1`, `CHORDUS_INDEX_KEY_V1`), never `NEXT_PUBLIC_`, never in the database, different per environment. A written escrow copy held by two Admins in a password manager (losing the key loses the data) |
| Rotation        | Yearly, and when anyone with key access leaves. New writes use the new version; a background job re-encrypts old rows. The index key rotates with a full re-index                                                                                                                                                |
| Decryption path | Only in server code after `guardApi` with the right permission and `aal2`, and every reveal writes a read audit (NFR-AUD-002). List and table views return masked values computed at write time (store `last4` alongside)                                                                                        |
| Erasure         | Deleting the ciphertext (and, for a whole category, retiring a key version) is effective "crypto-shredding", which also neutralises copies in backups once they age out                                                                                                                                          |
| Trade-off       | The database cannot sort or search these fields. That is acceptable: nobody needs to sort by NIC                                                                                                                                                                                                                 |

Supabase already encrypts the database and backups at rest at the platform level (SOC 2 scope, [Supabase SOC 2](https://supabase.com/docs/guides/security/soc-2-compliance)). Field encryption adds protection against a leaked backup, a leaked service key, an over-broad RLS policy, and the dashboard SQL editor.

### 4.4 Audit

Extend the Phase 0 append-only `audit_log` rather than replace it.

1. **Redaction (fix before Phase 1).** `audit_row_change()` stores `to_jsonb(old)` and `to_jsonb(new)` (migration lines 223 to 224). For Restricted columns, store only a marker and a keyed hash: `{"bank_account": {"changed": true, "h": "<hmac>"}}`. Pass the column list as trigger arguments (`tg_argv`), so each table declares its own redactions.
2. **More context columns.** `actor_type` (user, service, webhook, job, device), `actor_role` and `entity_id` at the time, `request_id`, `ip inet`, `user_agent`, `reason` (required for corrections and reveals), `source` (trigger, app, system). Set them through `set_config('chordus.request_id', …, true)` from the server per request, read in the trigger.
3. **System actors.** A `write_system_audit()` function executable only by `service_role`, for PayHere webhooks, ADMS device pushes, scheduled jobs and seed scripts. Today service-role writes land with `actor_id = null` and no label.
4. **Read logging.** Every reveal of a Restricted field, payslip or medical file download, and export writes `action = 'read.reveal' | 'read.download' | 'read.export'` with the field name (not the value), row count and file hash. Reads are high volume, so put them in a sibling table `access_log` with the same append-only triggers, or partition `audit_log` by month.
5. **Tamper evidence.** Add `prev_hash` and `row_hash` (SHA-256 over the row plus the previous hash) computed in a `before insert` trigger with a serialising lock. A daily job sends the latest hash to a place the database owner cannot edit (for example an email to the DPO and a commit to a private repo). An Admin "verify chain" button recomputes it. This answers the gap that the table owner can still `alter table … disable trigger` or drop the trigger (the immutability trigger stops DML, not DDL).
6. **Free-text actions.** `write_audit()` accepts any action text from any signed-in user (migration lines 185 to 211). Keep it, but tag these rows `source = 'app'` and validate `p_action` against an allow-list table, so a user cannot write a convincing fake "payroll.approved" entry.
7. **Retention.** 7 years by default (covers the five-year IRD rule plus a margin), configurable. Deletion only by dropping whole monthly partitions through a documented, dual-approved procedure that itself writes an audit entry.
8. **Who reads it.** Admins and the DPO. Reading the audit viewer is itself logged.

### 4.5 Secrets

- Configuration from environment variables only (CLAUDE.md). Split `lib/env.ts` into a public schema and a `server-only` `lib/env.server.ts` that validates secrets (service key, field keys, PayHere merchant secret, Resend key, BSP token) and **fails closed in production** when one is missing.
- A CI check that no variable containing `KEY`, `SECRET` or `TOKEN` is prefixed `NEXT_PUBLIC_`.
- Keep gitleaks; add GitHub secret scanning with push protection (free for public repos; for private repos it depends on the plan, unverified). PayHere merchant secrets are a known detector type ([GitGuardian](https://docs.gitguardian.com/secrets-detection/secrets-detection-engine/detectors/specifics/payhere_merchant_secret)).
- The Supabase secret (service) key is used only by server jobs that need it (webhooks, scheduled jobs). It is never needed for normal page rendering, because user requests run under the user's JWT and RLS.
- Rotate all secrets when an Admin or developer with access leaves. Keep a secrets register (name, where it lives, owner, last rotated) in the runbook.

### 4.6 Storage, files and external portals

- **Buckets**: private only. Separate buckets per tier: `hr-docs` (Restricted), `medical` (Restricted-Special), `payment-attachments`, `vouchers`, `payslips`, `consents`, `deliverable-links` (metadata only). Paths use UUIDs, never names or NICs. Policies on `storage.objects` scoped by bucket plus entity plus owner; in a private bucket every operation goes through RLS ([Supabase buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals)).
- **Signed URLs**: created server-side after the guard, with short expiry (5 minutes Restricted, 60 minutes Confidential). A signed URL cannot be revoked early without Supabase support (secondary source), so short expiry is the control. Signing with the service key bypasses RLS, so the guard check before signing is mandatory.
- **Uploads**: size and MIME allow-lists, image re-encoding to strip EXIF location from staff phone uploads, PDF and image only for HR documents. Malware scanning is advisory for the MVP (no built-in scanner confirmed).
- **Client portal** (R4-F14) and **freelancer portal** (R2-47): separate principal types (`portal_users` linked to `client_contacts` or `talent`), never `app_role = 'employee'`. RLS by membership (`client_id in (select … where user_id = auth.uid())`). Portal routes live under their own path with their own guards and cannot reach staff modules (404, like Phase 0).
- **Approval links without an account** (R4 5.2): see NFR-SEC-012 and threat model 5.4. Token of at least 128 random bits, stored hashed, scoped to one deliverable version and one action, expiring (default 14 days, policy data), revoked when a new version is sent. Approving a version that releases an invoice requires an email OTP to the named client contact.

### 4.7 POS device security and offline data

The POS is a PWA on a shared tablet or phone (R3 section 8). Cards go through a standalone bank terminal, Genie or Tap-to-Pay device, never through ChordusAM.

| Area            | Requirement                                                                                                                                                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Device identity | Each POS device is registered by a supervisor (device record plus a device key held in the browser as a non-extractable WebCrypto key). Unregistered browsers cannot open a shift. Devices can be revoked remotely                                                |
| Staff identity  | Cashiers unlock with a personal PIN on a registered device, tied to their ChordusAM account. Auto-lock after 2 minutes idle. Every sale, refund and void records the cashier                                                                                      |
| Offline queue   | IndexedDB queue **encrypted** with the device key. Holds only the catalogue, prices and pending sales. No customer records beyond the open sale, no Restricted data. Maximum offline window (for example 72 hours) and maximum offline sale value are policy data |
| Offline limits  | Offline: cash and "card on terminal, approval code X" only. Refunds, voucher redemption and deposit changes are blocked offline (R3 2.2)                                                                                                                          |
| Sync integrity  | Each queued sale has a client-generated UUID and a device sequence number. The server accepts each once (idempotent) and flags gaps in the sequence                                                                                                               |
| Card data       | Only last 4 digits and approval code are typed. Input validation rejects anything that looks like a full card number (Luhn check on 13 to 19 digits) in any free-text field                                                                                       |
| Cash controls   | Shift open float, blind cash count at close, variance above a threshold needs a supervisor who is not the cashier                                                                                                                                                 |
| Device hygiene  | Checklist: OS screen lock, automatic updates, no shared Google account, browser profile used only for POS. Lost device: revoke in ChordusAM and rotate the device key                                                                                             |

**Staff phones (self-service, mobile check-in).** Do not cache Restricted data offline. Payslips open as short-lived signed URLs, not saved in the PWA cache. Sign-out sends `Clear-Site-Data`. Mobile check-in captures location once at check-in, with the reason shown to the user.

### 4.9 Logging and monitoring

- **Application logs**: structured JSON, request ID on every line, **no Restricted values** (redact NIC, bank, salary, tokens in a logger wrapper). Vercel log retention is short on standard plans (unverified); send to a log drain if needed.
- **Error tracking** (for example Sentry): PII scrubbing on, no request bodies for HR, payroll and payment routes.
- **Alerts** (email to Admins and DPO, later WhatsApp): role or permission granted; MFA factor removed or reset; vendor or employee bank details changed; payroll run unlocked or edited after approval; more than N reveals of Restricted fields by one user in a day; bulk export; PayHere webhook with a bad signature or amount mismatch; POS sequence gap or large cash variance; audit hash chain mismatch; failed sign-ins spike.
- **Supabase**: review Auth logs and the dashboard audit trail monthly. Limit dashboard access (G-06).

### 6.4 Segregation of duties (SoD) matrix

**R** = may do it, **A** = approves it, **—** = may not. Rules in the last column apply even when one person holds two roles. AMPL is small (three Admins, one Finance person), so the matrix uses compensating controls where full separation is not possible.

| Duty                                                 | Employee / requester  | HR          | Finance              | Admin                    | Hard rule (enforced in DB or rules)                                                                 |
| ---------------------------------------------------- | --------------------- | ----------- | -------------------- | ------------------------ | --------------------------------------------------------------------------------------------------- |
| Grant or change a role or permission                 | —                     | —           | —                    | R (second Admin **A**)   | Granting Admin, Finance or `salary_viewer` needs a second Admin. No one grants to themselves        |
| Create employee record                               | —                     | R           | —                    | A                        | Creator cannot be the approver                                                                      |
| Change salary or contract terms                      | —                     | R           | —                    | A                        | Approver is not the employee concerned                                                              |
| Change an **employee's** bank details                | R (own, request only) | R (enter)   | A                    | —                        | NFR-SEC-025: dual approval plus call-back plus cool-off                                             |
| Prepare payroll run                                  | —                     | R           | —                    | —                        |                                                                                                     |
| Approve payroll run                                  | —                     | —           | —                    | A                        | Approving Admin is not the preparer; Admins' own lines reviewed by a different Admin (or the owner) |
| Release payroll payment (mark Paid, bank upload)     | —                     | —           | R                    | Backup only              | Payer is not the approver of the same run                                                           |
| Create vendor                                        | R (with permission)   | R           | A (before first pay) | R                        | Vendor bank or NIC must not match the requester or any employee (blind index)                       |
| Change a **vendor's** bank details                   | —                     | R (request) | R (verify call-back) | A                        | Requester, verifier and approver are three different people where possible; at least two            |
| Raise payment request                                | R (with permission)   | R           | —                    | R                        |                                                                                                     |
| Approve payment request above limit                  | —                     | —           | —                    | A                        | Not the requester (PLAN 2)                                                                          |
| Mark payment Paid                                    | —                     | —           | R                    | Backup only              | Not the requester **and** not the approver of that request                                          |
| Record income, expenses, receipts                    | —                     | —           | R                    | R                        |                                                                                                     |
| Bank reconciliation / month-end review               | —                     | —           | R                    | A (review)               | Reviewer is an Admin who did not approve that month's large payments, rotating                      |
| Upload attendance                                    | —                     | R           | —                    | R                        | HR's own punches flagged for Admin review                                                           |
| Approve leave or manual attendance                   | —                     | Recommend   | —                    | A                        | No self-approval (PLAN 2)                                                                           |

| Approve deletion of audit partitions or bulk erasure | —                     | —           | —                    | R + second Admin **A**   | DPO informed                                                                                        |

**Small-team fallback.** When only one Admin is available (PLAN 15 "all three Admins away"), payments above the limit wait or use a time-limited delegation (PLAN 15) recorded in the audit log, and the owner reviews every delegated approval within 5 working days. When Janaka is away, an Admin may act as payer, but never on a request that Admin approved.
